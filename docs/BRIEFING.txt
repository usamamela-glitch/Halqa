What Halqa Is

Halqa (حلقہ) is the Urdu word for constituency. It is a personal
constituency management app built exclusively for Usama Mela to manage
his parliamentary constituency of roughly 700,000 people across NA-83
Sargodha-II.

The app is not a public product. It is a private political intelligence
tool. Think of it as a CRM for a politician — but one that understands
how Pakistani politics actually works: the Qanungo administrative
structure, village-level dynamics, group loyalties, development demands,
and the importance of personal relationships with key people.

The core problem it solves: A Pakistani MNA interacts with hundreds of
villages, thousands of contacts, and constantly shifting political
dynamics. Without a system, everything lives in the MNA's head or in
WhatsApp notes. Halqa brings it all into one place — organised,
searchable, and eventually AI-analysable.

How the constituency is structured: Pakistani rural constituencies are
administratively divided by Qanungos (revenue officers who oversee a
group of villages). Usama has organised his app to mirror this: Qanungos
→ Villages → Contacts. Each village has election results (2018 and
2024), population, voter count, group dynamics (our group vs
opposition), development notes, contacts, and notes.

The end goal: Once the data is rich enough — every village documented,
key contacts added, dynamics filled in — Usama plans to run Claude AI
analysis on the entire dataset to get village-by-village strategic
recommendations for the next election. The app is, in a sense, building
the database that will power that analysis.

Current usage: The app is live at halqa-apps.vercel.app, added to
Usama's iPhone home screen as a PWA, and used daily in the field. A
handful of trusted colleagues also have access via the same URL.

The Journey — What We Went Through

This section exists so you understand why we are rebuilding, and so you
do not repeat the same mistakes.

How the original was built: The original app was built iteratively in a
Claude.ai chat session over many months. Claude Sonnet 4.6 wrote code,
sent zip files or individual files, and Usama pasted them into GitHub
manually via the web interface. Every change went: write code → download
file → Cmd+A on GitHub → delete → paste → commit → Vercel deploys. This
workflow, while functional, accumulated significant technical debt.

The ghost code problem (CRITICAL — do not repeat): The single most
persistent bug in the entire project was a ghost reference to a function
called importFromContacts in pages/village/[id].js. The story: we
attempted to build an "Import from Contacts" feature using the browser's
navigator.contacts API. We discovered it is not supported on iOS Safari.
We removed the feature — but we did it incrementally across multiple
edits, and a line calling importFromContacts on a button remained in the
file long after the function was deleted. Every time we edited the
village page and deployed, this orphaned reference caused a client-side
JavaScript crash — the infamous white screen with "Application error: a
client-side exception has occurred." We fixed it, it came back, we fixed
it again. It haunted us for weeks. Lesson: when you build the new app,
never leave a function call without its definition. Run npm run build
and check for errors before considering any file done.

The CSS duplication problem: Because we were sending whole files for
replacement, and because my local copy of the codebase occasionally
drifted from what was on GitHub, CSS blocks sometimes got duplicated.
The most notable case: a .dayToDay class appeared twice in
Home.module.css — once with height: calc(100vh - 160px) making a card
take up the full screen. Lesson: in the new app, use a proper local
development environment. Never paste-replace files blindly.

The image/notes saga: Notes images went through three formats:

1.  First: blob:// URLs (pasted images) — expired when browser closed,
    gone overnight

2.  Second: full <img src="..."> HTML saved in the body column — URLs
    worked but reconstruction on reload was unreliable

3.  Third (current): [IMG:path] markers in body, reconstructed into img
    tags on load using fresh Supabase Storage URLs

Format 3 works correctly. Stick with it in the new app.

The Vercel auto-deploy breakdown: After many failed deployments (syntax
errors, missing functions, etc.), Vercel's GitHub webhook stopped
triggering. We spent hours troubleshooting — disconnect/reconnect
GitHub, deploy hooks, the 100 deployment/day free tier limit. Lesson:
use a proper git workflow with Claude Code. Commit only when the build
passes locally.

The contenteditable notes editor: The note editor used a contenteditable
div instead of a <textarea>. This was chosen for better mobile typing
feel and inline image support. It caused persistent issues: auto-save
comparing wrong HTML snapshots, paste events inserting rich HTML with
invisible text colors, cursor position resets. The block-based textarea
approach we tried as a replacement caused even more problems (lost
formatting, broken autosave). We ended up back on contenteditable with
careful paste handling. For the new app, consider whether a proper rich
text library (like Tiptap or Quill) would be worth the dependency, or
stick with the proven contenteditable approach with careful handling.

Things that worked well from the start:

-   Supabase integration — fast, reliable, well-documented

-   CSS Variables for theming — changing --green globally changed the
    entire app

-   The Qanungo → Village → Contact structure — perfect fit for the
    constituency

-   The pinning system and Main Groups auto-aggregation — elegant and
    loved by the user

Why We Are Rebuilding

The current app works. Usama uses it daily. The data is valuable and
growing. So why rebuild?

1. Clean code. The current codebase has accumulated over 50 incremental
edits via paste-replace on GitHub. It has duplicate CSS blocks, ghost
function references that occasionally resurface, inconsistent component
structure, and no type safety. A fresh build with Claude Code — which
can run the build locally and catch errors before they reach Vercel —
will produce a codebase that is maintainable and debuggable.

2. Offline mode (most important new feature). Usama is an MNA who spends
days in his rural constituency. Signal is unreliable. The current app
cannot load without internet. He loses data because he has to jot things
in iPhone Notes and transfer them later. The new app must be
offline-first: data stored locally on the device, synced to Supabase
when connection is available. This is the single most impactful change.

3. New features. Several features were discussed and deferred because
adding them cleanly to the current codebase was too risky. The new app
will include all of them from the start (see New Feature List section).

4. Better UI/UX. The current UI is functional but minimal — cards that
blink between pages, no animations, basic styling. The new app should
feel like a polished native app: page slide transitions, spring
animations on modals, a bolder visual design (Option B), and a
professional feel consistent with a product that could eventually be
sold to other politicians.

5. Commercial potential. There are 1,064 parliamentary constituencies in
Pakistan. A well-built, beautiful, AI-powered version of this app could
be sold to other MNAs and MPAs. The rebuild should be built with that
quality bar in mind, even though the immediate user is one person.

Instructions to Claude Code

You are building a brand new Next.js app from scratch. Here is exactly
how to approach this.

Step 1: Set up the project

-   npx create-next-app@latest halqa-v2 --no-typescript --no-tailwind
    --no-eslint

-   Install dependencies: npm install @supabase/supabase-js dexie
    framer-motion

-   Dexie.js for IndexedDB (offline storage), Framer Motion for
    animations

-   Copy the Supabase credentials from the Tech Stack section into
    lib/supabase.js

Step 2: Set up offline-first architecture FIRST Before building any UI,
set up the data layer:

-   Create a Dexie database (lib/db.js) that mirrors the Supabase
    schema: tables for qanungos, villages, contacts, notes,
    general_notes, day_note

-   Write a sync service (lib/sync.js) that:

    -   On app load (if online): pulls latest from Supabase into Dexie

    -   After any local write: immediately writes to Dexie, then pushes
        to Supabase in background

    -   If Supabase push fails: queues the operation and retries when
        connection restored

-   All React components read from Dexie, never directly from Supabase

-   This architecture means the UI is always fast (local reads) and
    works offline

Step 3: Build components in this order

1.  Layout and navigation shell with Framer Motion page transitions

2.  Home screen (Qanungos tab, General tab, Search tab)

3.  Qanungo page

4.  Village page with all four tabs

5.  Main Groups page

6.  Day to Day scratchpad

7.  Note editor

8.  Quick-Add contact modal

9.  Analysis section (last — needs Claude API key setup)

Step 4: Run npm run build after every component Do not accumulate
multiple changes before building. Build and fix after each component.
This prevents the cascading errors that plagued the original.

Critical rules — do not break these:

1.  Never leave a function call without its definition. If a button
    calls handleSomething, that function must exist in the same file
    before you commit.

2.  Check for ghost references before every build. Search the file for
    any function names used in JSX that are not defined above.

3.  Never save blob:// URLs. Images must be uploaded to Supabase Storage
    and saved as [IMG:path] markers.

4.  Always include both FN and N fields in vCard generation.

5.  No authentication. Do not add a login system.

6.  Mobile only. Do not waste time on responsive desktop layouts.

7.  Keep the same database. Do not drop or rename existing columns. You
    may add new columns and tables.

On the offline implementation: The offline mode is the most complex part
of this build. Take it seriously. Test it by:

-   Loading the app

-   Turning off WiFi/mobile data

-   Adding a contact, editing a village's dynamics

-   Turning connectivity back on

-   Verifying the changes appear in Supabase

If you are unsure about the offline architecture, research the
Dexie.js + Supabase sync pattern before starting. There are
well-documented approaches for this.

On the Claude AI Analysis: The Claude API key will be provided by Usama.
Build a simple settings screen where he can enter it. Store it in
localStorage (acceptable for this personal app). When analysis is
triggered, pull all relevant data from the local Dexie database, format
it into a well-structured prompt, and stream the response from the
Claude API. The prompt should include the user's own notes and
descriptions — they are the most valuable data for analysis.

On deployment: Once the app is working locally, create a new Vercel
project (do not overwrite the existing halqa-apps project, which should
remain live until the new app is tested). Connect to a new GitHub repo
usamamela-glitch/halqa-v2. Once Usama confirms the new app is working
correctly, he will update his iPhone home screen bookmark.

Finally: This app is used by a Member of Parliament in Pakistan to
manage his political constituency. The data inside it is sensitive
political intelligence. Build it with that seriousness. The person who
will use it most is not a developer — he is a politician with an iPhone,
in the field, meeting people all day. Every interaction should be fast,
intuitive, and forgiving of mistakes. When in doubt, optimise for speed
of data entry and reliability over cleverness.
